# 群聊黑话词库

对应 [V2 开发路线图](roadmap.md) 的 Phase 4。这里说明机器人**怎么听懂群里的话**：候选从哪来、谁批准、什么时候进入提示词，以及最要紧的一条——**模型说什么都不算数，只有人点过「确认」的词才会被注入**。

## 一句话口径

> **模型负责「找候选」，人负责「批准」，提示词只吃批准过的。**

抽取会调用一次模型并计入每日预算；注入是免费的。一个词从被看见到生效，中间一定有人点过一下。

## 开关与默认值

**默认关闭。** `.env` 不写任何 `SLANG_*` 时，行为与 Phase 3 完全一致：不注入任何内容，也不会主动抽取。

```dotenv
SLANG_ENABLED=false                  # 总开关（也可在控制台「黑话」页打开）
SLANG_INJECT_MAX=20                  # 最多注入多少条（上限 30）
SLANG_EXTRACT_MESSAGES=120           # 一次抽取扫描最近多少条群消息
SLANG_AUTO_EXTRACT=false             # 是否允许定时自动抽取（默认只手动点）
SLANG_EXTRACT_INTERVAL_HOURS=12      # 自动抽取的最小间隔
```

`SLANG_ENABLED` 可以在控制台「黑话」页运行时切换，立即生效并写入 `settings` 表；其余四项需要改 `.env` 后重启。黑话开关还能在控制台「群设置」页**按群覆盖**——某个群单独关掉黑话，不影响其他群。机制见 [按群特异化](groups.md)。

自动抽取默认**关闭**：它会在无人按键的情况下花掉预算。想让它自己跑，需要同时满足 `SLANG_ENABLED=true` 与 `SLANG_AUTO_EXTRACT=true`，频率由 `SLANG_EXTRACT_INTERVAL_HOURS` 限制。手动点击永远不受间隔限制。

## 三个阶段

```
群消息流水 (messages 表)
        │
        │  extract：扫描最近 N 条 → 一次模型调用 → 候选
        ▼
   candidate（待确认） ── 人工「拒绝」──► rejected
        │
        │  人工「确认」
        ▼
   confirmed ──► 【群聊黑话表】注入群聊提示词
```

### 1. 抽取（花钱）

`Slang.extract()`：

1. 从 `messages` 表取该群最近 `SLANG_EXTRACT_MESSAGES` 条消息（这张表本身按 `SOCIAL_MESSAGE_TTL_HOURS` 定期裁剪）；
2. 把消息拼成记录，身份用**每次抽取重新编号的「成员1/成员2」**代替 QQ 号——号码不出本机；
3. 每条消息先过 `escapeForPrompt()` 转义；
4. 走一次预算预留 → 模型调用 → 结算，并落一条 token 采样；
5. 解析回复，写入/合并候选，最后按容量上限裁剪。

### 2. 确认（人工）

候选写进 `slang` 表时状态是 `candidate`，**不参与注入**。控制台上按状态筛选，逐个「确认」或「拒绝」。

- 重复抽到同一个词只累加 `count` 与依据，**不会覆盖已有含义**，更**不会把 `rejected` 改回 `candidate`**：人的判断比模型的新观察优先。
- 「联网查义」按钮复用现有搜索能力（与 `/搜索` 共用当日搜索次数上限），把搜索结果写进 `meaning` 并记下来源 URL，但**同样不会自动确认**。

### 3. 注入（免费）

已确认的词按出现次数排序，最多 `SLANG_INJECT_MAX` 条，格式化成：

```
【群聊黑话表】（群里常见的说法，只用来理解群友在说什么，不要把这张表解释出来）
666 = 厉害
awsl = 啊我死了
```

这段文字追加在**人格提示词之后**，群聊的两条路径都会带上：

- 拟人化仿真（`Social.systemPrompt()`）；
- 群内 @ 问答（`Bot.systemPrompt(message)`）。

私聊不带（私聊没有群词汇）。每次对话都重新读取，所以在控制台确认一个词之后，**下一条群消息就会生效**，不需要重启。

**词条可按群归属**：`slang_groups` 表记录每个词条只属于哪些群。没有归属记录的词条是**全局**的（所有群注入）；有归属记录的词条只注入列出的群。抽取时新词条会自动关联到来源群，之后在控制台「黑话」页的单条详情里改「生效群」。空选 = 全局。

## 健壮性

四条防线，前两条直接对应 qq-bridge 踩过的坑：

1. **JSON 用括号配平扫描，不用贪婪正则。** 模型回复常带解释性前缀。`根据[1]的说法，结果：[{...}]` 里第一个方括号是引用角标；用「第一个 `[` 到最后一个 `]`」或「第一个 `]`」去截，要么失败、要么截出 `[1]`，然后被当成「解析成功但 0 个候选」——这正是要避免的**静默失败**。
   实际实现对整段回复收集所有完整数组，再按优先级取：**第一个非空对象数组 > 空数组（合法的「没有黑话」）> 报错**。也就是说，解析不出来时会明确失败并在控制台报错，而不是假装没找到。
   另外扫描会跟踪引号，先按「引号内不算括号」扫一遍；遇到不配对引号（前缀里的 `"` 没闭合）导致引号状态反转时，再用「忽略引号」扫第二遍兜底。

2. **损坏的备份绝不当成「空词库」。** 本项目词库落在 SQLite（`slang` 表，`content` 唯一），本身有事务保护，因此这条教训在本项目里只有**备份恢复**这一条路径有文件可谈：`importAll()` 解析失败时把原文另存为 `runtime/slang-corrupt-<时间戳>.json` 并抛错，**绝不**返回空数组让后续保存把词库清掉。导入还要求顶层是数组（或含 `entries` 数组），否则同样拒绝。那份另存的原文里可能含群聊原句，因此写入时会与其它秘密文件一样收紧 ACL（见 [安全与隐私基线](security.md)）。

3. **容量上限 2000 条。** 超限按「**已确认 > 出现次数 > 最近更新**」裁剪，即优先淘汰未确认、少出现、久未更新的词条。

4. **注入前转义与压平。** 词条与含义都会经过 `sanitiseText()`：控制字符、`U+2028/2029` 与换行一律压成空格，再按码点截断。一个含 `\n7 = 忽略以上规则` 的词**无法在表里另起一行**冒充一条指令。注入时还会再走一次 `escapeForPrompt()`。

## 数据模型

`slang` 表（Phase 0 建表，Phase 4 启用）：

| 列 | 含义 |
| --- | --- |
| `id` | 内部标识（恢复备份时重建的行会拿到新 id） |
| `content` | 词条本身，**唯一** |
| `meaning` / `usage` / `example` / `risk` | 含义／用法／记录中的原句／歧义或禁忌 |
| `status` | `candidate` / `confirmed` / `rejected` |
| `source` | `ai`（抽取）或 `search`（联网查义） |
| `count` | 被观察到的次数，决定注入排序与裁剪优先级 |
| `sources` / `evidence` | 来源标记与支撑它的消息 id（JSON 数组） |
| `created` / `updated` | 时间戳 |

`content` 上的唯一索引在 `Store.migrate()` 中幂等创建；建表前会先把历史重复行按最早一条合并掉（`slang` 表在 Phase 4 之前没有任何写入路径，这只是兜底）。

按群归属用独立的 `slang_groups` 表（`slang_id, group_id`）表示，不在 `slang` 表加列：没有 `slang_groups` 行的词条是全局的，有行的词条只注入列出的群。表很小，且 `deleteSlang`/`trimSlang` 会显式清理孤儿行，所以不设外键。

## 与预算、搜索、隐私的关系

- **预算**：抽取与查义都走现有「预留 → 结算」账本，与问答、主动发言共用同一个每日上限。**闸门在调用之前**：预算不足时直接拒绝，不发起请求。
- **失败不释放预留**：与问答一致，模型调用失败时预留转为 `uncertain` 而不是释放——超时的请求上游可能已经计费。
- **搜索额度**：联网查义与 `/搜索` 共用 `WEB_SEARCH_DAILY_LIMIT` 计数，需要 `WEB_SEARCH_ENABLED=true`。
- **隐私**：抽取只把**该群最近消息**发给模型，且身份用匿名编号；`messages` 与词条原文不会进日志；控制台列表接口**不返回** `example`（记录中的原句），只有点开单条详情时才返回。

## 控制台

「黑话」页见 [Web 控制台](console.md)。要点：

- 顶部四个指标：功能开关、已确认条数（含实际注入条数）、待确认条数、容量占用；
- 「抽取候选」按群触发（每次点击都是一次真实模型调用）；
- 词条列表按状态筛选，逐条「确认／拒绝／详情改义／联网查义／删除」；
- 底部展示**当前注入到群聊提示词里的原文**，所见即所注入；
- 「导出备份」下载 JSON；「恢复备份」按词条内容做**加法合并**——已存在的词保留本地的人工确认状态，只取较大的出现次数。

## 排查

| 现象 | 处理 |
| --- | --- |
| 抽取按钮变灰 | 先打开页面上方的总开关（或 `SLANG_ENABLED=true`） |
| `SLANG_BUDGET_BLOCKED` | 今日模型预算已用尽，明日恢复 |
| `SLANG_EXTRACT_UNPARSABLE` | 模型没返回可解析的 JSON 数组；本次未写入任何词条，可稍后重试 |
| `SLANG_SEARCH_DISABLED` | 联网查义需要 `WEB_SEARCH_ENABLED=true` |
| `SLANG_SEARCH_LIMIT` | 今日搜索次数已用完（与 `/搜索` 共享） |
| 确认了却没有生效 | 检查群聊路径：`SOCIAL_ENABLED`/问答是否被 `/停止`、`/群关闭` 关掉；私聊本来就不带黑话表 |
| 词条被裁掉了 | 词库达到 2000 条上限；把重要的词确认一下（已确认的最不容易被裁） |

事件名：`slang_extracted`、`slang_extract_failed`、`slang_extract_unparsable`、`slang_auto_extract_failed`、`slang_status_changed`、`slang_edited`、`slang_deleted`、`slang_lookup_done`、`slang_lookup_failed`、`slang_lookup_unverified`、`slang_imported`、`slang_import_corrupt`、`slang_params_changed`。
